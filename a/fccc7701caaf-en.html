Self-hosting Isn't Just About Docker: The Hidden Pitfalls

Docker makes deployment easy, but self-hosting requires a robust network infrastructure to avoid security flaws and downtime.

Docker simplifies deployment by letting users copy a .yaml file and run docker compose up -d, but self-hosting requires far more than just spinning up containers. Without a proper network infrastructure, even a well-configured server can quickly become unstable and insecure. Local IP changes break access, unencrypted HTTP exposes credentials over Wi-Fi, and raw ports invite automated port scanners to probe your system.

The real challenge lies in building a reliable foundation: setting up a reverse proxy (such as Caddy or Nginx Proxy Manager) to handle traffic, configuring local DNS (via Pi-hole, AdGuard Home, or Unbound) to route human-readable domain names like jellyfin.home.arpa instead of IP addresses and port numbers, and securing remote access without port forwarding. Services like Tailscale, WireGuard, or Cloudflare Tunnels provide encrypted mesh networks, eliminating the need for exposed ports or complex firewall rules while maintaining strict authentication.

Data preservation is another critical aspect often overlooked. Mounting a Docker volume to the host SSD is not a backup—it’s just live data. A proper 3-2-1 backup strategy (three copies, two different media, one off-site) is essential to prevent data loss from hardware failures. Tools like Borg Backup, Restic, or Kopia automate snapshots, database dumps, and encrypted syncs to cloud or secondary storage.

Docker’s default network isolation can also cause operational issues. By default, containers are isolated in internal bridge networks, which may prevent external reverse proxies from accessing them unless custom Docker networks are properly designed. Additionally, using :latest tags for container images risks silent failures during schema migrations. Pinning versions and backing up databases before updates are crucial to avoid unexpected downtime.
